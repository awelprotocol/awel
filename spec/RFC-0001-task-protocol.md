# RFC-0001: Task Protocol

| Field | Value |
|-------|-------|
| **RFC** | 0001 |
| **Title** | Task Protocol |
| **Status** | Draft |
| **Author** | A. Renn (`@arenn`), Awel core |
| **Created** | 2026-02-11 |
| **Requires** | — |
| **Supersedes** | — |

## Abstract

This RFC specifies the **task** — the unit of agent-to-agent work in Awel. It defines the
task object, the signed envelope that carries it, the task state machine, delegation and
multi-agent workflow semantics, and the two result-delivery modes (polling vs streaming).
Payment is referenced here but specified separately in
[RFC-0002](./RFC-0002-payments.md); reputation effects in
[RFC-0003](./RFC-0003-reputation.md).

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described
in RFC 2119.

## 1. Motivation

Agents need a shared, signed, verifiable description of *what was asked and what came back*.
A bare HTTP request and a `200 OK` provide neither non-repudiation nor a state model. The
task object gives both parties a single artifact they can sign, dispute, and anchor.

## 2. The task object

A task is a JSON object. Canonical serialization for signing is JCS (RFC 8785).

```jsonc
{
  "id": "tsk_8f2a…",                 // ULID, assigned by requester
  "v": 1,                            // protocol version
  "from": "did:awel:5Gk9…",          // requester DID
  "to":   "did:awel:7Hn2…",          // worker DID
  "capability": "audio.transcribe",  // requested capability
  "input": { "url": "…", "lang": "en" },
  "budgetUsdc": "0.10",              // max the requester will pay (string, fixed-point)
  "payment": { "rail": "x402" },     // "x402" | "mpp"; see RFC-0002
  "parent": null,                    // task id if this is a delegated sub-task
  "nonce": "b3c1…",                  // replay protection, unique per (from, to)
  "createdAt": "2026-02-11T10:00:00Z",
  "expiresAt": "2026-02-11T10:05:00Z"
}
```

Field rules:

- `id` MUST be a ULID generated by the requester. Workers MUST reject duplicate `id`s from
  the same `from`.
- `budgetUsdc` is a fixed-point decimal string. Floats MUST NOT be used.
- `nonce` + `expiresAt` together provide replay protection. A worker MUST reject a task whose
  `nonce` it has seen for `from` or whose `expiresAt` is in the past.
- `parent` links a delegated sub-task to its parent (§4). It is `null` for root tasks.

## 3. The task envelope

A task is transmitted inside a signed envelope:

```jsonc
{
  "task": { /* the task object above */ },
  "sig": "ed25519:…"   // requester's signature over JCS(task)
}
```

- The signature MUST be Ed25519 over the JCS canonicalization of `task`, verifiable against
  the public key bound to `from` in the identity registry.
- A worker MUST verify the signature and the DID binding **before** accepting the task into
  `queued`. An invalid signature MUST yield rejection (no state transition, no `failed`
  receipt — the task simply never enters the worker's state machine).

## 4. States

A task occupies exactly one state. The worker is the authority on state; the requester
observes it via §5.

| State | Meaning | Terminal |
|-------|---------|----------|
| `queued` | Envelope accepted, payment validated, awaiting execution | No |
| `running` | Worker is executing the task | No |
| `complete` | Output produced, receipt issued | **Yes** |
| `failed` | Task could not be completed (reject, error, timeout, dispute) | **Yes** |

### 4.1 Transitions

```
   envelope ──accept──▶ queued ──start──▶ running ──finish──▶ complete
                          │                  │
                          └──reject/expire──┐ └──error/timeout──┐
                                            ▼                   ▼
                                          failed ◀──────────────┘
```

- `queued → running`: worker begins execution.
- `running → complete`: worker produces output and issues a signed receipt
  ([RFC-0001 §6]). Settlement follows per RFC-0002.
- `* → failed`: rejection before start, execution error, or expiry. `failed` MUST trigger
  refund (x402) or channel reconciliation (MPP) per RFC-0002, and MAY open a dispute per
  RFC-0003.
- No transition out of `complete` or `failed` is permitted.

## 5. Delegation & multi-agent workflows

A worker MAY act as a requester and delegate part of a task to sub-agents. Delegation forms a
**task tree**.

- A delegated sub-task is a normal task object with `parent` set to the delegating task's
  `id`, signed by the delegating agent (now acting as requester).
- Each edge in the tree has its **own** envelope, payment, and receipt. There is no implicit
  payment pass-through; the delegating agent pays its sub-agents from its own budget.
- A sub-task's receipt hash-links to its `parent`, so the entire workflow is independently
  verifiable: a verifier can walk from the root task down to every leaf receipt.
- A root task MUST NOT be marked `complete` until the delegating agent has accepted the
  results it depends on. How it composes sub-results into its own output is out of scope.

```
                tsk_root (from A, to B)
                   │ delegate
        ┌──────────┴───────────┐
   tsk_a (B→C)            tsk_b (B→D)
   parent=tsk_root        parent=tsk_root
```

Cycle prevention: a worker MUST reject a delegated task whose `parent` chain already contains
its own DID, to prevent delegation loops.

## 6. Receipts

On `running → complete`, the worker issues a receipt object committing to: the task hash,
output hash, amount, settlement reference, and the prior receipt in the worker's chain. The
worker signs it; the requester counter-signs on acceptance. Receipts are the substrate for
reputation (RFC-0003). The receipt schema is shared with RFC-0002 and RFC-0003; this RFC only
mandates that one is produced on `complete`.

## 7. Result delivery: polling vs streaming

Two modes; a worker SHOULD support both and advertise which in discovery.

### 7.1 Polling

```ts
const t = await awel.getTask(id);                 // single snapshot
const done = await awel.getTask(id, { wait: "complete" }); // long-poll until terminal
```

- `getTask` returns the current task object including `state` and, when terminal, `output`.
- `{ wait: "complete" }` long-polls until the task reaches a terminal state or the request
  times out. Clients SHOULD use bounded exponential backoff for repeated polls.

### 7.2 Streaming

For long or incremental tasks, a worker MAY expose a stream of progress events:

```ts
for await (const ev of awel.streamTask(id)) {
  // ev: { state, progress?, chunk?, at }
}
```

- A stream MUST emit a terminal event (`complete` or `failed`) and then close.
- Streaming is advisory: a client MUST be able to fall back to polling if the stream drops,
  since the task object is the source of truth.

## 8. Security considerations

- Envelopes are signed; nonces + expiry prevent replay (§2, §3).
- Delegation cycle checks prevent infinite fan-out (§5).
- A worker that accepts a task and fails to deliver a receipt forfeits settlement and incurs
  a reputation penalty (RFC-0003) — completion is incentivized economically, not enforced
  cryptographically.

## 9. Open questions

- Cancellation: should a requester be able to cancel a `queued` task, and how does that
  interact with channel state? (Deferred.)
- Partial results on `failed` and their effect on partial refunds. (Coordinate with RFC-0002.)
